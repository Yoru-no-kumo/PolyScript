# PolyScript AI — 아키텍처

버전 0.3 · 한국어 · 검토본 · 2026-10-19 (Asia/Tokyo)

## 1. 확정 경계와 구조의 상태

현재 제품은 Windows 개인용 데스크톱 앱이다. 기술 선택은 [의사결정 v0.3](../decisions/architecture_decisions.v0.3.ko.md)의 ADR-007에 남긴다. 아래 책임 구분은 기존 기능 요구를 정리한 **논리 구조 제안**이며 모듈·프로세스·서비스 개수를 확정하지 않는다.

과거 Control Plane·서버 Worker·공유 DB·Learning Server를 새 앱의 필수 배포도로 사용하지 않는다. 외부 실행 범위가 미결이므로 완전 로컬 실행이나 네트워크 연결 의무도 가정하지 않는다.

## 2. 논리 책임 — 제안

| 책임 | 담당할 일 | 미결사항 |
| --- | --- | --- |
| 사용자 경험 | 프로젝트·상태·검수·재생·출력 | UI 프레임워크·화면 |
| 애플리케이션 제어 | 요청·실행 정책·취소·재시도 | 내부 호출·프로세스 간 통신 |
| 도메인 | 화자·캐릭터·원문·번역·채택·변경 영향 | 코드 경계·스키마 |
| 처리 실행 | 단계 의존성·자원·체크포인트·실패 처리 | 큐·스케줄러·동시 실행 수 |
| 엔진 연동 | FFmpeg·ASR·화자 분리·정렬·번역 연결 | 엔진·모델·런타임·실행 위치 |
| 저장 | 메타데이터·미디어 참조·산출물·개인 라이브러리 | DB·경로·파일 형식 |
| 이력·복구 | 생성 근거·사용자 변경·진단·복원 | 로그·보존·복구 목표 |

`사용자 → 데스크톱 UI → 애플리케이션 제어 → 도메인 / 처리 실행 → 엔진`

`도메인 / 처리 실행 → 저장·산출물·출처 이력 → 검수 / 재생 / 내보내기`

논리 책임을 구분한다고 운영체제 프로세스까지 분리한 것은 아니다.

## 3. 처리·검수 흐름 — 기존 요구 유지

1. 프로젝트에 미디어를 입력하고 파일과 설정을 확인한다.
2. 오디오 준비·발화·화자 분석·음성 인식·정렬 등 필요한 처리를 실행한다.
3. 결과를 후보로 저장하고 입력·엔진·모델·설정·실행 이력을 연결한다.
4. 검수 또는 별도 채택 규칙으로 공식 데이터를 구성한다. 자동 채택 조건은 미결이다.
5. 사용자가 원문·번역·화자·캐릭터·시간 정보를 수정한다.
6. 영향받는 결과를 오래된 상태로 식별하고 필요한 범위를 재생성한다.
7. 채택한 데이터를 반복 청취·Shadowing과 Script/Subtitle 출력에 사용한다.

이는 개념적 흐름이며 고정 실행 순서가 아니다. 기존 27개 개념적 Stage의 전체 목록은 확보되지 않았다. 위 흐름으로 그 목록을 대체하거나 이름·번호를 임의 복원하지 않는다. 개념 단계 수는 실제 Worker·Job 개수를 뜻하지 않는다.

## 4. 긴 작업과 앱 수명주기

**유지:** 진행 상태·오류 원인 확인, 재시도, 가능한 완료 결과의 재사용이 필요하다. 미완료·손상 결과를 정상 산출물로 채택하지 않는다.

기존 “브라우저 종료 후 서버 작업 지속”을 “앱 종료 후 실행 지속”으로 자동 변환하지 않는다.

| 상황 | 결정할 동작 — 모두 미결 |
| --- | --- |
| 창 닫기 | 종료·트레이 유지·작업 안내 |
| 앱 종료 | 취소·안전 중단·별도 실행부 계속 실행 |
| 절전·재부팅·강제 종료 | 체크포인트·재개 범위·중복 실행 방지 |
| 엔진 실패·GPU 메모리 부족 | 재시도·자원 해제·대체 엔진 |
| 입력 이동·외장 드라이브 분리 | 파일 재연결·중단·복구 |

**제안:** 저장 가능한 작업 상태와 결과 확정 경계를 먼저 설계한 뒤 프로세스 배치를 선택한다. 상태 enum과 큐 제품은 확정하지 않는다.

## 5. 저장과 변경 영향

**유지:** 메타데이터와 대용량 파일의 책임을 구분하며 캐시는 공식 원본으로 사용하지 않는다. 현재 DB 제품은 미선정이다.

원문 수정은 번역·자막에, 화자 연결 수정은 화자별 Script와 재사용 지식에 영향을 줄 수 있다. 실제 의존관계를 기준으로 영향을 판단한다.

**제안:** 분석 버전·사용자 수정·현재 채택본을 구분하여 새 분석과 차이를 비교한다. 버전 단위·충돌 해결·물리 저장 형식은 미결이다. 상세 원칙은 [데이터 정책 v0.3](../data/data_policy.v0.3.ko.md)를 따른다.

## 6. 엔진·품질·자원

**유지:** 엔진은 가능한 범위에서 기능·지원 언어·모델 버전·입출력·시간 정보·자원 요구를 표현한다. 모델은 실제 대상 미디어의 Benchmark로 비교한다. 정답·검수 기준, 모델·설정·장비 버전, 품질·처리 시간·자원 사용을 기록하는 방향을 유지한다. 정량 합격 기준은 미결이다.

Progressive Refinement와 백그라운드 고품질 재처리는 기존대로 **제안 / 실험 대상**이다. 고정 2회 처리나 v1 의무로 승격하지 않는다.

## 7. Learning

기본 화자 재사용과 검증된 지식 활용은 제품 흐름에 연결한다. 고급 모델 학습은 조건부 흐름이다.

`허용된 근거 → 학습 후보 → Dataset 검증 → 학습 → 평가 → 승인 → 모델 적용`

Core/Learning의 책임 구분은 참고하되 물리적 실행 배치는 미결이다. 실제 학습 구현 전 실행 격리·자원 경합·데이터 접근·승인 주체·모델 교체와 복귀를 결정해야 한다. 현재 학습 서버나 자동 학습 서비스를 설치하기로 한 것은 아니다.

## 8. 연결·보안·배포

외부 API·원격 처리·모델 다운로드·업데이트·진단 전송의 범위는 각각 미결이다. 외부 전송을 채택할 때 데이터·목적·수신처·보관 조건·실패 동작을 명시하는 방향을 제안한다. 현재 클라우드 동기화·텔레메트리 도입을 결정하지 않는다.

음성·화자 프로필·키·설정 보호의 필요성은 남는다. 과거의 보안 보호 수단 제안을 확정으로 승격하지 않으며 Windows 자격증명 저장·암호화·앱 잠금·설치 방식은 미선정이다.

## 9. 다음 결정의 연결 관계 — 제안

미디어 복사/참조와 앱 종료 시 작업 동작을 먼저 정하면 저장·실행 구조를 구체화할 수 있다. 이후 목표 장비와 미디어를 기준으로 UI·DB·실행 방식·엔진을 비교한다. 이는 구현 일정이나 기술 선택의 확정이 아니다.
